# Bugfix — spec-viewer-files-tree-scroll-latency

## 정의
spec-viewer 사용자를 위해 `--all` 모드에서 파일 수가 많은 디렉터리를 스크롤할 때 체감되는 지연을 재현·수정하는 성능 버그픽스 스펙이다.

## 재현 절차
1. 환경: `spec-viewer` release 빌드, `--all` 모드로 마크다운 파일이 수천~수만 개인 디렉터리(예: 평평한 구조로 20,000개 `.md` 파일)를 열고 트리 패널(`Files`)에 대부분/전부가 보이는 상태(디렉터리 폴딩 없이 최상위에 많은 leaf가 바로 노출되는 구조, 또는 여러 디렉터리를 펼친 상태).
2. 입력: `ui::render`의 실제 호출 경로(`app::update(Action::Key(Down))` → `ui::render`)를 20,000개 항목의 `TreeSource::Files(FsTree)`로 구성한 `AppState`에 대해 60회 연속 실행 — 빠른 트랙패드 스크롤/화살표 키 연타가 짧은 시간에 여러 이벤트를 큐에 쌓는 것과 동일한 패턴(`main.rs`의 `run_loop`는 이벤트 1개당 리듀서+전체 `terminal.draw` 1회를 동기 수행, 배치 없음).
3. 관찰 결과: `std::time::Instant`로 격리 측정 —
   - 항목 500개: 스텝당 0.73ms, 60스텝 43.8ms
   - 항목 5,000개: 스텝당 2.47ms, 60스텝 148ms
   - 항목 20,000개: 스텝당 9.07ms, 60스텝 540ms
   `ui/tree_panel.rs::render_files`에 임시 계측을 넣어 원인을 분리: 20,000개 항목 기준 `build_files_items`(스크롤 위치·변경 여부와 무관하게 `FsEntry` 전체를 순회해 새 `String`/`Line`/`Span`/`TreeItem`을 매 프레임 새로 할당) 4.25ms, `frame.render_stateful_widget`(`tui_tree_widget`의 자체 `flatten()` 포함) 1.8ms — `build_files_items`가 스텝당 비용의 약 절반을 차지하며, 트리 항목 수에 비례해 커짐. 뷰포트(화면에 실제로 보이는 행 수)와 무관하게 전체 항목 수에 비례한다.
   같은 `AppState`/`ui::render` 경로를 `.kiro` 모드(`TreeSource::Kiro`)로 쓰면 스펙 개수가 보통 수십 개 이하라 이 비용이 체감되지 않는다(`render_kiro`의 기존 주석이 "이 크레이트 규모(.kiro 아래 소수의 스펙)에서는 캐시 없이도 저렴"이라고 명시) — 이번 결함은 `--all` 모드가 동일한 "캐시 없음" 가정을 훨씬 큰 항목 수에 그대로 적용한 데서 발생한다.

## Boundary Context
- **In scope**: `ui/tree_panel.rs::render_files`/`build_files_items`가 매 렌더(=매 스크롤/키 이벤트) 항목 전체를 다시 만드는 비용.
- **Out of scope**: `tui_tree_widget`가 자체적으로 `render_stateful_widget` 내부에서 수행하는 `flatten()` 비용(외부 크레이트 동작, 이번 수정 범위 밖), `.kiro` 모드(`render_kiro`)의 동일 패턴(현재 스펙 개수 규모에서는 체감 비용 없음, 별도 결함 아님), `FsTree::scan` 자체(파일 목록 산출 비용, spec-viewer-watch-startup-latency에서 이미 측정·확인해 무관함).

## Behaviors

### 1. 현재 동작 (결함)
- 1.1: [`--all` 모드에서 `Files` 트리에 수천~수만 개 항목이 보이는 상태에서 스크롤(연속 키/휠 이벤트)] → 매 스크롤 이벤트마다 트리 전체 항목을 다시 순회해 새 `TreeItem` 목록을 할당하며, 항목 수가 많을수록(20,000개 기준 스텝당 9ms) 스크롤이 눈에 띄게 끊기고 느려짐.
- 1.2: [1.1과 동일 조건] → 이 지연은 화면에 실제로 보이는 행 수(뷰포트)가 아니라 트리 전체 항목 수에 비례해 커짐 — 스크롤이 화면 안에서만 위치를 옮기는 동작인데도 항목 수 전체를 다시 처리함.

### 2. 기대 동작
- 2.1: [1.1과 동일 조건] → 트리 항목(`entries`)과 검색 하이라이트(`search_matches`)가 이전 프레임과 동일하면 `TreeItem` 목록을 다시 만들지 않고 재사용해, 스크롤 시 항목 수와 무관하게 빠르게 반응함(재구성 비용 제거분만큼 스텝당 시간 감소).
- 2.2: [트리 항목 또는 검색 하이라이트가 실제로 바뀐 경우(파일 변경으로 인한 재스캔, 검색어 변경 등)] → 다음 렌더에서 새 내용이 정확히 반영됨(캐시가 실제 변경을 놓치지 않음).

### 3. 불변 동작 (회귀 방지)
- 3.1: [`--all` 모드에서 파일 변경 발생, 항상] → 여전히 트리가 최신 내용(추가/삭제/이름변경된 파일)으로 갱신됨(요구사항 7.4 유지, `resync`의 `FsTree::scan` 재호출 경로는 변경 없음).
- 3.2: [트리 검색(2.10) 실행 중, 항상] → 일치 노드 하이라이트가 여전히 정확히 표시됨.
- 3.3: [`.kiro` 모드(`TreeSource::Kiro`), 항상] → 이번 수정은 `Files` 경로에만 적용되며 `render_kiro` 동작은 그대로임(회귀 없음).
- 3.4: [폴더 펼치기/접기(`Right`/`Left`), 항상] → 선택·펼침 상태가 여전히 정확히 반영됨.
