# Design — spec-viewer-kiro-mode-freeze

## 정의
fs 이벤트가 유발하는 갱신 작업을 UI 스레드 밖에서 수행해, 파일 변화가 계속 일어나는 저장소에서도 `.kiro` 모드 네비게이션·스크롤이 멈추지 않게 하는 최소 변경 설계다.

## 원인 (Root Cause)
- `app/mod.rs::update`의 `Action::Fs(_)` 분기(415행)는 이벤트 경로를 보지 않고 `resync(state)`를 호출한다. `resync`(1137행)의 kiro 분기는 `loader::load_snapshot(&state.kiro_root)`(루트 아래 모든 스펙 파일·spec.json·steering 재판독) + `spec::build` + `spec::sort_specs` + `refresh_current_doc`(현재 문서를 디스크에서 재판독해 마크다운을 다시 파싱·렌더)까지 **UI 스레드에서** 수행한다.
- `main.rs::run_loop`은 `Action::Fs`마다 `step()`(갱신+전체 드로우)을 동기 실행하므로, 갱신 작업 동안 키·마우스 이벤트가 큐에 쌓인다. 감시 디바운스가 300ms인데 이벤트가 연속되면(활성 저장소 — 에이전트가 스펙을 계속 쓰는 환경) 갱신이 끝나자마자 다음 갱신이 시작되어 UI가 지속적으로 블로킹된다(1.1). `--no-watch`에서는 이 경로 자체가 없어 즉시 반응한다(1.2).
- 근거: 같은 `Action::Fs → resync` 경로를 공유하는 `--all` 모드 실측 — 유휴 CPU 41%(watch ON) vs 0.8%(`--no-watch`). 갱신 작업이 상시 UI 스레드를 점유함의 직접 증거다. `.kiro` 루트 아래는 대부분 표시 대상 파일이라 이벤트 대부분이 갱신으로 이어지며, 갱신 "작업량"의 축소는 `spec-viewer-fs-event-targeted-update`의 영역이다.

## 수정 방식
- `resync`를 **계산**(파일 I/O·파싱: 새 `TreeSource` 생성 + 갱신된 `DocView`)과 **적용**(상태 대체)으로 분리한다. `Action::Fs`는 계산을 백그라운드 워커에 넘기고(이미 진행 중이면 "재요청" 플래그만 설정) 즉시 반환한다. 워커의 완료 결과는 감시 이벤트와 같은 인바운드 채널로 전달한다 — 채널 페이로드를 `Fs(FsEvent) | ResyncDone(TreeSource, Option<DocView>)` 열거형으로 통합한다. UI 스레드는 완료 도착 시 적용만 수행하며, 적용 시점에 재요청 플래그가 켜져 있으면 계산을 다시 예약한다(연속 이벤트 병합).
- 수동 갱신 `r`(요구사항 7.6)도 같은 경로를 쓴다.
- 완료 적용은 기존 `refresh_current_doc`의 선택 유지 규칙(7.5)을 그대로 따른다.

**기각한 대안**:
- 갱신 비용 축소(영향받은 파일만 재판독): `spec-viewer-fs-event-targeted-update`의 영역. 이 설계는 갱신 로직의 크기와 무관하게 UI 블로킹을 없애는 스케줄링 변경으로, 그 스펙과 직교해 조합된다.
- 디바운스 연장(300ms→수 초): 지연만 늘 뿐 갱신 중 블로킹은 그대로므로 2.1("즉시 반응")을 만족하지 못한다.

## 검증 속성
- (a) 결함 재현: 수정 전 `update(state, Action::Fs(..))` 한 호출이 대형 픽스처에서 네비게이션 입력 수십 회 분에 상응하는 시간을 동기로 소모함을 시간 어서션으로 고정한다(1.1/1.2).
- (b) 기대 동작: 수정 후 `update(Action::Fs)`가 상태를 바꾸지 않고 즉시 반환하며(워커 예약만), `ResyncDone` 적용 후 트리·문서가 최신 내용이 됨을 어서션한다. 워커 진행 중 도착한 추가 이벤트가 재요청 플래그를 설정해 갱신이 손실되지 않음을 확인한다(2.1/2.2).
- (c) 불변 동작: 기존 갱신 관련 테스트(최신 내용 반영 7.1~7.4, 선택·펼침 유지 7.5, `r` 수동 갱신 7.6)가 완료-적용 경로에서도 통과하고, `--all` 모드 갱신도 같은 워커를 쓰며 회귀가 없음을 확인한다(3.1~3.4).

## 영향 범위
- 변경 파일: `spec-viewer/src/app/mod.rs`(`resync` 계산/적용 분리, `Action` 열거형 확장, 재요청 플래그), `spec-viewer/src/main.rs`(`run_loop`의 인바운드 열거형 처리, 워커 예약), `spec-viewer/src/watch/mod.rs`(포워드 스레드의 페이로드 열거형 전환 — 감시 로직 자체는 무변경).
- Boundary Commitment 위반 없음: `watch`는 감시·전달만(파일 I/O 없음), `app`은 상태 전이만, 파일 I/O가 UI 스레드에서 사라지는 것은 기존 "main은 얇은 I/O 래퍼" 원칙의 강화다.
