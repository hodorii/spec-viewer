# Design — spec-viewer-mouse-scroll-freeze

## 정의
마우스 이벤트가 상태 변화 없이도 매번 전체 렌더를 유발하지 않도록 입력 모드·소비 구조를 최소 변경해, 마우스 스크롤이 키보드 스크롤과 동일하게 즉시 반응하게 하는 버그픽스 설계다.

## 원인 (Root Cause)
- `main.rs::main`(351행)은 `crossterm::event::EnableMouseCapture`를 실행한다. 이 명령은 crossterm 0.29에서 `?1000h`(누름/뗌) + `?1002h`(버튼 드래그) + **`?1003h`(모든 모션 추적)** + `?1006h`(SGR)을 함께 켠다(crossterm-0.29.0/src/event.rs 321~329행). 포인터가 터미널 위에서 움직이는 동안 `MouseEventKind::Moved`가 초당 수십~수백 개 스트리밍된다.
- `main.rs::run_loop`은 이벤트 1개당 `step()`(리듀서+`terminal.draw()`)을 동기 실행한다(배치 없음). `app/mod.rs::handle_mouse`는 `Moved`를 `_ => {}`(502행)로 무시하지만 렌더는 `step` 안에서 항상 수행되므로, 상태가 전혀 바뀌지 않은 모션 이벤트도 매번 전체 프레임을 그린다.
- 휠 이벤트 1개는 `scroll_panel_under_pointer`(500~501행)가 문서 3행 또는 트리 `key_down()` 3회를 동반한다. 트랙패드 관성으로 모션+휠이 몰리면 이벤트당 렌더가 누적되어 큐가 밀리고, 화면은 멈춘 뒤 일괄 점프한다(1.1/1.2). 키보드는 발생률이 낮아(자동 리핏 ~30/s) 같은 렌더 비용에도 큐가 밀리지 않는다 — 재현 절차의 장치별 차이.
- 근거: `--all ~/w` 실측 이벤트당 CPU 1.7~3.5ms(트리 펼침·접힘). 모션 200/s + 휠 90/s 수준이면 렌더만으로 코어를 소진해 "유입 > 소진"이 성립한다. 소스 전수 확인 결과 `Moved`의 소비자는 없다(드래그는 1002h의 `Drag`, 휠은 마우스 모드가 켜져 있으면 항상 전달).

## 수정 방식
1. **모션 추적 해제**: 활성화를 `EnableMouseCapture` 대신 필요한 모드만 켜는 시퀀스로 교체한다 — `\x1b[?1000h` + `\x1b[?1002h` + `\x1b[?1006h`. `?1003h`를 요청하지 않아 모션 스트림이 원천 차단된다. 소비자가 없는 이벤트의 제거이므로 동작 보존적이고, 클릭(1000h)·드래그 제스처(1002h)·휠·SGR 좌표(1006h)는 그대로 유지된다(요구사항 9.1~9.7). 종료 복원은 기존 `DisableMouseCapture`를 그대로 쓴다(켜지 않은 모드의 해제는 no-op).
2. **입력 버스트 병합**: `run_loop`의 `poll(100ms)` 분기에서 이벤트 1개를 읽어 리듀서를 수행한 뒤, 대기 중인 이벤트를 `poll(Duration::ZERO)`로 모두 소진(리듀서만 연속 수행)하고 렌더는 1회만 수행한다. `Control::Quit`은 드레인 중 즉시 탈출한다. 휠/키 버스트가 몰려도 렌더 횟수가 이벤트 수에 비례하지 않는다.

**기각한 대안**:
- 상태 변화 시에만 렌더하는 더티 플래그: 리듀서 전반의 침습적 변경이며 이번 결함의 본질(입력 장치별 반응성 차이)에 필수가 아니다.
- 마우스 캡처 전면 비활성: 9.1~9.7 마우스 제스처 전부가 깨진다.

## 검증 속성
- (a) 결함 재현: 수정 전 활성화 시퀀스가 `?1003h`를 포함함을 직렬화 어서션으로 고정하고, `Moved` 이벤트가 리듀서에서 상태를 전혀 바꾸지 않음(렌더만 유발)을 `handle_mouse` 단위 테스트로 고정한다(1.1/1.2의 전제).
- (b) 기대 동작: 수정 후 활성화 시퀀스에 `?1003h`가 없고(2.2의 원천 차단) 1000/1002/1006이 유지됨을 어서션한다. 휠 버스트 N개가 렌더 1회로 수렴함을 드레인 로직의 단위 테스트로 확인한다(2.1).
- (c) 불변 동작: 기존 마우스 제스처 테스트(9.1~9.7 경로) 전부 통과, 휠 3행 이동 유지(3.1), 드레인 도입 후에도 Quit을 포함한 이벤트가 하나도 손실되지 않음(3.3)을 어서션한다.

## 영향 범위
- 변경 파일: `spec-viewer/src/main.rs`(마우스 모드 활성 시퀀스, `run_loop` 드레인), `spec-viewer/src/app/mod.rs`(무변경 또는 `update` 재사용만).
- `spec-viewer` design.md의 Boundary Commitment("main은 얇은 I/O 래퍼", "ui는 상태를 읽기만 한다") 위반 없음 — 렌더 스케줄링은 여전히 `main`의 소유 영역이다.
