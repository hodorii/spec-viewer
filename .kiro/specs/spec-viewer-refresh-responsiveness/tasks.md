# 구현 계획 - spec-viewer-refresh-responsiveness

## 정의
스펙 문서를 편집하며 트리와 문서를 보는 spec-viewer 사용자를 위해, 재스캔의 백그라운드화, 문서 렌더 캐시, 부분 갱신, 좁은 패널 날짜 축약을 구현 단위로 나눈 실행 계획이다.

- [x] 1. 날짜 축약 표시
- [x] 1.1 좁은 패널에서 MM-DD 단계 추가
  - 실패하는 렌더 테스트부터: 날짜 전체가 안 들어가는 폭에서 `MM-DD`가 보이고, 그것도 안 들어가는 폭에서는 날짜가 없고 문서명과 진행률이 그대로이며, 전체가 들어가는 폭의 표시는 변경 전과 같다. 경계 폭 N과 N-1 두 곳을 모두 검증한다
  - `MM-DD`는 `format_modified_date`에서 파생하는 함수로 만든다. 날짜 단계(시각 포함, 날짜, `MM-DD`, 생략) 중 첫 적합 단계를 고르는 함수로 기존 시각 판정을 대체한다(SSoT)
  - _DoneWhen: 경계 폭 테스트가 통과하고 일치 강조와 날짜 없는 행의 표시가 변경 전과 같으며 기존 트리 테스트가 통과한다_
  - _Requirements: 4.1, 4.2, 4.3, 4.4_
  - _Difficulty: low_
  - _Boundary: ui::tree_panel, app::loader_

- [x] 2. 문서 렌더 캐시
- [x] 2.1 캐시 구성과 로드 경로 연결
  - 실패하는 단위 테스트부터: 같은 경로와 폭에서 두 번째 로드는 읽기와 렌더를 하지 않고(호출 횟수 카운터) 같은 결과를 주며, 수정 시각이나 크기나 폭이 달라지면 다시 읽고, 삭제되면 삭제 표시 경로로 가며, 17번째 항목이 들어오면 가장 오래 쓰이지 않은 항목이 빠진다. 재사용 결과의 파일 정보가 새로 읽은 결과와 같다
  - 렌더 결과 타입(`Rendered`, `Footnote`, `HeadingAnchor`, `FileInfo`, `DocView`)에 `Clone`을 파생하고, `AppState`가 캐시를 소유하며 선택 경로(`resolve_selection`, `load_for_selection`)가 캐시를 거치게 한다. 새로고침과 크기 변경 경로는 항상 최신 상태를 확인한다
  - _DoneWhen: 캐시 단위 테스트가 통과하고 같은 문서를 다시 선택해도 읽기 횟수가 늘지 않으며 기존 새로고침과 삭제 표시 테스트가 통과한다_
  - _Requirements: 2.1, 2.2, 2.3, 2.4, 2.5_
  - _Difficulty: mid_
  - _Boundary: app::doc_cache, app(AppState, resolve_selection), app::loader, markdown 타입 파생_

- [x] 3. 백그라운드 재스캔
- [x] 3.1 재스캔 조정기
  - 실패하는 단위 테스트부터: 요청이 진행 중에 여러 번 들어와도 추가 실행은 한 번이고, 세대를 올리면 이전 요청의 결과가 버려지며, 스레드가 패닉하면 결과 없이 진행 중 표시가 풀리고 다음 요청이 수행된다. 동시에 진행 중인 재스캔은 최대 하나다
  - 세대가 바뀌면 대기 요청을 버리고 새 요청은 옛 스레드를 기다리지 않고 시작한다. 스레드 생성 실패는 동기 재스캔으로 대체한다(이 둘도 테스트한다)
  - 스캔 대상 함수는 주입 가능하게 두어 테스트가 느린 가짜 스캔으로 겹침을 검증한다
  - _DoneWhen: 합치기, 세대 폐기, 패닉 복구 테스트가 타이밍 비의존(카운터와 채널 신호)으로 통과한다_
  - _Requirements: 1.1, 1.4, 1.5, 1.7_
  - _Difficulty: high_
  - _Boundary: app::rescan_
- [x] 3.2 상태 반영과 실행 루프 연결
  - 실패하는 통합 테스트부터: 백그라운드 모드에서 변경 이벤트 직후 입력이 처리되고(재스캔 미완료 상태에서) 완료 후 트리가 갱신되며 정렬 키, 선택, 펼침, 스크롤 위치가 유지되고 열린 문서가 삭제됐다면 삭제 표시가 나온다. 기본(동기) 모드의 기존 테스트는 그대로 통과한다
  - 소스 전환과 뿌리 변경(`ApplySourceSwitch`, `handle_switch_mode`)에서 세대를 올린다. 반영 직전에 현재 정렬 키로 다시 정렬한다(재스캔 중 정렬을 바꾼 경우를 테스트). 루프는 입력 타임아웃 때도 완료를 확인하고 결과가 있을 때만 다시 그린다.
  -  후반부(정렬 재적용, 열린 문서 갱신)는 기존 동기 재스캔과 공유한다
  - _DoneWhen: 통합 테스트와 기존 전체 테스트가 통과하고 실행 파일이 변경 이벤트 처리 중에도 입력에 반응한다_
  - _Requirements: 1.2, 1.3, 1.6, 1.8, 5.2_
  - _Difficulty: high_
  - _Boundary: app, main_
  - _Depends: 3.1_

- [x] 4. 부분 갱신
- [x] 4.1 변경 영향 판정과 부분 갱신
  - 실패하는 단위 테스트부터: 경로가 열린 일반 문서 하나이고 존재하면 재스캔 요청 없이 그 문서만 최신으로 읽고(캐시 우회) 세 소스 각각에서 트리 행 수정일 항목이 새 값으로 바뀐다. 경로가 없는 이벤트나 수동 새로고침이거나 정의 보기가 열려 있거나 다른 경로가 섞이거나 `spec.json`과 `tasks.md`이거나 파일이 사라졌으면 전체 재스캔으로 간다. 문서가 줄어들면 스크롤이 새 마지막 줄 안으로 조정된다
  - _DoneWhen: 허용과 거부 경로 테스트가 통과하고 부분 갱신 때 재스캔 호출 횟수가 0이다_
  - _Requirements: 3.1, 3.2, 3.3_
  - _Difficulty: mid_
  - _Boundary: app_
  - _Depends: 3.2_

- [x] 5. 검증
- [x] 5.1 읽기 전용과 전체 회귀
  - 재스캔, 캐시, 부분 갱신이 감시 디렉터리에 파일을 만들거나 바꾸지 않음을 확인하고 전체 테스트를 통과시킨다
  - _DoneWhen: 실행 전후 디렉터리 내용이 같다는 테스트와 전체 테스트가 통과한다_
  - _Requirements: 5.1, 5.2_
  - _Difficulty: low_
  - _Depends: 1.1, 2.1, 4.1_
- [x] 5.2 실제 실행 확인
  - 큰 디렉터리 파일 모드에서 새로고침 중 키 입력에 반응하는지, 같은 문서 재선택이 즉시 보이는지, 기본 폭과 좁은 폭에서 날짜 단계가 맞는지 `cargo run`으로 확인한다
  - _DoneWhen: 기본 실행과 좁은 폭 한 곳의 실제 화면에서 위 세 가지가 확인된다_
  - _Requirements: 1.2, 2.1, 4.2_
  - _Difficulty: low_
  - _Depends: 5.1_
