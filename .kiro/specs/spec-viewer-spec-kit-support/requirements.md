# Requirements — spec-viewer-spec-kit-support

## 정의
spec-viewer 사용자를 위해 GitHub spec-kit(`.specify/` + `specs/<NNN-이름>/`) 프로젝트를 `.kiro` 프로젝트와 동등하게 진행 상태를 알 수 있는 방식으로 조회 전용 브라우징하는 기능이다.

## Boundary Context
- **In scope**: `.specify/` 루트 자동 인식, `specs/<NNN-이름>/` 아래 기능별 문서(`spec.md`/`plan.md`/`tasks.md`/`research.md`/`data-model.md`/`quickstart.md`/`contracts/`) 트리 표시, 산출물 존재 여부 기반 진행 상태 배지, `tasks.md` 체크박스 진행률 재사용, `.kiro`와 공유하는 진행 상태 표시 방식(가변 길이 마일스톤), 기존 `.kiro` 상태 표시의 회귀 방지 및 개선(승인 게이트 전부 승인 vs 구현 완료 구분, 게이트 개수가 스펙마다 다른 경우).
- **Out of scope**: `specify` CLI 실행/연동(프로젝트·기능 생성, 계획·작업 생성 커맨드), `.specify/`의 확장(extensions)·프리셋·훅·체크리스트 기능, 파일 편집(뷰어 자체는 읽기 전용 — 외부 에디터로 여는 것은 `spec-viewer-editor-mode`가 이미 제공), git 확장(번호 붙은 기능 브랜치) 연동, `contracts/` 내부 파일(OpenAPI 등) 형식별 특수 렌더링.

## Acceptance Criteria

### 1. spec-kit 프로젝트 인식과 진입
- 1.1: [실행 인자로 지정된 디렉터리 또는 그 상위 어딘가에 `.specify/` 디렉터리가 있고, 더 가까운 위치에 `.kiro/` 디렉터리는 없음] → 뷰어가 spec-kit 모드로 열리고 그 프로젝트의 기능 트리가 표시됨.
- 1.2: [탐색 경로 상에서 `.kiro/`와 `.specify/`가 같은 디렉터리에 함께 존재] → `.kiro/`가 우선 선택되어 기존 동작(`.kiro` 모드)이 그대로 유지됨.
- 1.3: [지정 디렉터리 위로 `.kiro/`도 `.specify/`도 없음] → 기존과 동일하게 루트 탐색 실패로 처리되어 탐색 경로를 포함한 오류가 출력되고 비제로 종료됨(동작 변화 없음).
- 1.4: [`--all` 옵션이 함께 지정됨] → 기존과 동일하게 `.specify/` 유무와 무관하게 지정된 디렉터리를 일반 마크다운 트리로 표시함(우선순위상 `--all`이 spec-kit 인식보다 앞섬).

### 2. 기능 트리 표시
- 2.1: [spec-kit 모드로 진입] → `specs/` 아래의 기능 디렉터리 각각이 트리 노드로 표시되고, 이름은 디렉터리명 그대로(번호 접두사 포함) 나타남.
- 2.2: [기능 노드를 펼침] → 그 기능 디렉터리에 실제로 존재하는 문서만 `spec.md → plan.md → tasks.md → research.md → data-model.md → quickstart.md → contracts/` 순서로 자식 노드로 나열되고, 존재하지 않는 문서는 나열되지 않음.
- 2.3: [기능 디렉터리 안에 이 순서에 없는 다른 마크다운 파일이 있음] → 목록 끝에 파일명 그대로 나열되어 존재가 드러남(무시되지 않음).
- 2.4: [`specs/` 디렉터리 자체가 없거나 비어 있음] → 빈 기능 트리로 표시되고 오류 없이 계속 동작함.
- 2.5: [기능 디렉터리 안에 `spec.md` 등 인식 대상 문서가 하나도 없음(빈 기능 디렉터리)] → 자식 없는 빈 노드로 표시되고 오류 없이 계속 동작함.

### 3. 진행 상태 배지(공통 표시 방식)
- 3.1: [기능/스펙 노드 표시, 그 노드가 추적하는 마일스톤이 하나 이상 있음] → 완료로 볼 수 있는 마일스톤 개수와 그 노드가 실제로 추적하는 마일스톤 총 개수가 `n/총개수` 형태로 이름 옆에 표시됨.
- 3.2: [같은 트리 안에서 서로 다른 두 노드가 추적하는 마일스톤 총 개수가 서로 다름] → 각 노드는 자신이 실제로 추적하는 개수 기준으로 독립적으로 표시되며, 어느 한쪽 개수에 맞춰 다른 쪽 표시가 왜곡되지 않음.
- 3.3: [노드가 추적할 마일스톤이 하나도 없음] → 진행 배지 없이 이름만 표시됨.
- 3.4: [노드의 모든 마일스톤이 완료로 표시됨] → 다른 진행 중 노드와 시각적으로 구분되는 강조 표시가 나타남.

### 4. spec-kit 기능의 마일스톤 판정
- 4.1: [기능 디렉터리에 `spec.md`가 있음] → "명세" 마일스톤이 완료로 판정됨.
- 4.2: [기능 디렉터리에 `plan.md`가 있음] → "설계" 마일스톤이 완료로 판정됨.
- 4.3: [기능 디렉터리에 `tasks.md`가 있음] → "작업 분해" 마일스톤이 완료로 판정됨.
- 4.4: [기능 디렉터리에 `plan.md`/`tasks.md`가 아직 없음] → 해당 마일스톤은 완료로 판정되지 않되, 있는 마일스톤만으로 진행 상태가 표시됨(요구사항 3.1).
- 4.5: [항상] → spec-kit에는 "산출물이 모두 존재함" 이상의 구현 완료·검증 여부를 알려주는 별도 표시가 없다는 것이 이 기능의 알려진 한계로 남아 있으며, `tasks.md`까지 존재하면 모든 마일스톤이 완료로 표시됨(요구사항 3.4의 강조 표시 대상).

### 5. `.kiro` 상태 표시 회귀 방지 및 개선
- 5.1: [`.kiro` 스펙의 `approvals`에 기록된 게이트 중 일부만 승인됨] → 그 스펙에 실제로 기록된 게이트 개수를 총 개수로 삼아 승인된 개수가 표시됨(요구사항 3.1과 동일 형식).
- 5.2: [`.kiro` 스펙의 기록된 게이트가 모두 승인됐으나, 아직 구현 완료를 나타내는 후속 상태에 도달하지 않음] → "모든 게이트 승인됨" 표시가 나타나되, 요구사항 5.3의 "구현까지 완료됨" 표시와는 서로 다르게 나타남.
- 5.3: [`.kiro` 스펙이 구현 완료를 나타내는 후속 상태에 도달함] → 요구사항 5.2의 "게이트 전부 승인" 표시와 구분되는, 완료를 나타내는 표시가 트리에 나타남.
- 5.4: [`.kiro` 스펙이 표준 게이트 중 일부만 기록함(예: `bugfix.md` 전용 경로로 진행되어 일부 게이트가 애초에 존재하지 않는 경우)] → 실제로 기록된 게이트만으로 진행 상태가 정확히 표시되고, 기록되지 않은 게이트가 있는 것처럼 표시되지 않음.
- 5.5: [`.kiro` 스펙의 `spec.json`이 없거나 파싱에 실패함] → 기존과 동일하게 경고 배지가 표시되고 문서 노드는 정상 표시됨(동작 변화 없음).

### 6. tasks.md 체크박스 진행률
- 6.1: [기능/스펙 노드에 `tasks.md`가 있고 체크박스가 하나 이상 있음] → 완료/전체 체크박스 개수가 `n/m` 형태로 표시되고, 전부 완료 시 다른 진행률과 구분되는 강조 표시가 나타남(기존 `.kiro` 표시와 동일 형식).
- 6.2: [`tasks.md`는 있지만 체크박스가 하나도 없음] → 체크박스 개수 대신 "진행률 없음" 안내가 표시됨(기존과 동일).

### 7. 문서 조회
- 7.1: [기능/스펙 문서 노드 선택] → 해당 파일 내용이 문서 패널에 마크다운으로 렌더링됨(다이어그램 포함, 기존 렌더링 파이프라인 그대로).
- 7.2: [`contracts/` 하위 파일 선택] → 파일 내용이 문서 패널에 일반 텍스트/코드 블록 수준으로 표시됨(형식별 특수 렌더링 없음).

### 8. 읽기 전용
- 8.1: [항상] → spec-kit 루트(`.specify/`, `specs/`) 아래 어떤 파일도 생성·수정·삭제하지 않음.

### 9. 편집모드와의 상호작용
- 9.1: [spec-kit 문서가 문서 패널에 표시된 상태에서 편집 키 입력] → 추가 구현 없이 기존 편집모드가 그대로 동작해 외부 에디터로 열림.
