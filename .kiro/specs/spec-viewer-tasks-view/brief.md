# 브리프: spec-viewer-tasks-view

## 문제
spec-viewer 사용자(스펙 작업을 진행/리뷰하는 개발자)는 `tasks.md`를 봐도 작업 하나하나의 번호, 상태, 난이도, 의존 관계, 근거(요구사항/업무프로세스)를 한눈에 파악하기 어렵다. 지금은 `tasks.md`를 다른 문서와 똑같이 일반 마크다운으로만 렌더링해서, `_Requirements:_`/`_Boundary:_`/`_Depends:_`/`_Difficulty:_`/`_BizProcess:_` 태그나 `(P)` 병렬 표식이 전부 평범한 텍스트 한 줄로만 보이고, 그 태그가 가리키는 실제 근거(요구사항 조항, 다른 작업, 업무프로세스 단계)로 이동할 방법이 없다.

## 현황
- `src/spec/mod.rs::build_spec`가 `tasks.md`를 `DocKind::Tasks` 슬롯으로 읽어 `count_progress`(`src/spec/progress.rs`)로 체크박스를 평면 집계(`done/total`)하는 것까지만 한다 - 번호, 중첩, 태그는 전혀 파싱하지 않는다(인용: `progress.rs` 자체 문서 주석 "no attempt is made to parse task numbering... or nesting").
- 트리 패널(`src/ui/tree_panel.rs`)은 이 `done/total`을 `n/total` 배지로만 보여준다(`milestone_badge_spans`/`progress_style` 재사용).
- `tasks.md`를 선택해 열면 다른 문서와 동일하게 `markdown::render`를 거친 일반 렌더링만 보인다 - `_Requirements: 1.1, 1.2_` 같은 줄은 볼드 텍스트로만 보이고 클릭, 이동 수단이 없다.
- 크로스 문서/위치 이동은 전무하다: `scroll_to`/`jump_heading`(`src/app/mod.rs`)은 **현재 열린 문서 안에서만** 스크롤 위치를 옮긴다. 한 스펙 안의 다른 문서(`requirements.md`/`bugfix.md`/`biz-process.md`)로 전환하면서 특정 위치로 점프하는 기능 자체가 없다(코드 전수 검색으로 확인, "jump"/"navigate"/"goto" 키워드 매치 없음).
- `_Depends:`/`_BizProcess:` 등 태그가 가리키는 대상은 전부 **같은 스펙 디렉터리 안**에 있다 - `_Requirements:`/`_Boundary:`는 `requirements.md`(또는 `bugfix.md`)의 조항 번호, `_Depends:`는 같은 `tasks.md` 안의 다른 작업 번호, `_BizProcess:`는 같은 스펙 `biz-process.md`의 드릴다운 노드를 가리킨다. 스펙을 넘나드는 참조는 없다(이번 세션에서 실제 작성한 `spec-viewer-files-mode-sort/tasks.md`의 `_Requirements: 1.1, 1.2, 1.3, 2.1, 2.2, 2.3, 4.1, 4.2_` / `_Depends: 1_` / `_BizProcess: BP-FILES-SORT.L2-D1_` 등으로 인용 확인).
- **수정(사용자 피드백, "빼고 해보자")**: `L2-D1`류 드릴다운 ID는 메서드론 공식 템플릿에 없던 이 저장소만의 즉석 관행이었음을 확인(agentic-psdd 커밋 이력 조사로 확인, 최초 템플릿부터 지금까지 고유 ID가 없음). 이 스펙에서는 그 ID 체계를 되살리지 않고 간다 - `_BizProcess:_` 태그 값은 고유 ID가 아니라 **biz-process.md의 L1/L2 제목 텍스트 자체**(예: "작업 메타데이터 확인")이고, Navigator는 원문에서 그 제목 줄을 찾아 이동한다.

## 목표 상태
- `tasks.md`를 열면(또는 전용 전환 키로) 작업이 번호, 체크박스 상태, `(P)` 표식과 함께 구조화된 목록으로 보인다 - `_Requirements:_`/`_Boundary:_`/`_Depends:_`/`_Difficulty:_`/`_BizProcess:_` 같은 메타 태그가 본문과 구분되는 배지/서브라인으로 보인다.
- 메타 태그는 단순 텍스트가 아니라 **이동 가능한 링크**다: `_Requirements:_`/`_Boundary:_`의 번호를 고르면 같은 스펙의 `requirements.md`(또는 `bugfix.md`)에서 그 조항 줄로 바로 이동, `_Depends:_`의 작업 번호를 고르면 같은 `tasks.md` 안의 그 작업으로 이동, `_BizProcess:_`가 가리키는 제목(이름)을 고르면 같은 스펙 `biz-process.md`에서 그 제목 줄로 이동한다.
- 참조 대상이 없거나(문서 누락) ID가 실제로 존재하지 않을 때는 조용히 깨지지 않고 평범한 텍스트처럼 보이거나 이동 실패를 알려준다(정확한 동작은 설계 단계에서 확정).
- 다른 `.kiro` 프로젝트가 태그 이름이나 번호 체계를 다르게 쓰더라도(예: `_Req:_`, `_Ref:_`), 설정으로 "이 태그 -> 이 파일" 매핑만 바꾸면 그대로 동작한다(아래 접근 참고).

## 접근
전용 Tasks 뷰 + 크로스 참조 이동(사용자 선택, 추천안). 토론을 거치며 두 관점으로 나눠 정리(사용자 제안):

- **방법론 설정** (methodology settings, 데이터): "이 프로젝트는 어떤 메서드론 표기를 쓰는가"를 선언하는 쪽. 핵심은 **태그 이름 -> 대상 파일** 매핑(예: `_Requirements:_`/`_Boundary:_` -> `requirements.md`/`bugfix.md`, `_BizProcess:_` -> `biz-process.md`, `_Depends:_` -> 자기 자신 `tasks.md`)과 `DONE`/`_DoneWhen:_` 같은 표기 이표기(alias) 목록. 참조 해석은 대상 문서를 깊이 구조 파싱하지 않고 그 파일의 **원문 텍스트에서 번호나 제목 문자열을 찾는** 범용 검색으로 충분하다(토론 중 사용자 제안의 핵심 단순화) - 그래서 설정은 "새 파서"가 아니라 "매핑 표"로 끝난다. AGENTS.md의 `{{SPECS}}`/`{{STEERING}}` 같은 Paths 표와 같은 성격의 선언이라, 방법론(이 저장소는 `methodology` 서브모듈)이 바뀌거나 다른 `.kiro` 프로젝트가 다른 태그를 쓰면 이 설정만 바꾸면 된다.
- **방법론 보기** (methodology viewing, 동작): 구조화된 Tasks 뷰 렌더링 + 그 안의 **Navigator**(가칭) - 메타 태그의 번호/ID를 "방법론 설정"의 매핑으로 대상 파일을 찾고, 그 파일에서 텍스트 검색으로 위치를 찾아, 트리+뷰어 틀 안에서 이동을 실행하는 역할. Navigator는 설정(어디서 찾을지)과 뷰(무엇을 보여줄지)를 분리하는 경계면이다.
  - `biz-process.md`가 지금처럼 제목 깊이 표기든, 나중에 dg의 `bizprocess`/`bpmn` 펜스(아래 제약 인용)로 바뀌든 Navigator는 똑같이 동작한다 - 어느 쪽이든 제목/번호 문자열은 마크다운 원문에 그대로 있다. 다만 대상이 다이어그램 펜스 안이면 "그 블록까지" 이동이 현실적 정밀도이고, 다이어그램 내부 특정 노드 하이라이트까지는 범위 밖(아래 범위의 제외 참고).

대안으로 "기존 n/total 배지 개선"(변경 범위는 작지만 태그 구조화, 이동 요구를 전혀 충족 못함)과 "다음 미완료 작업 탐색"(이동 요구의 부분집합만 다룸)을 검토했으나, 사용자가 명시적으로 "전용 Tasks 뷰"와 "링크 찾아가기"를 함께 요구해 기각.

## 범위
- **포함**:
  - `tasks.md` 자체의 구조 파싱(작업 번호, 체크박스 상태, `(P)` 표식, DONE/`_DoneWhen:_` 기준 줄, 메타 태그 줄 추출) - 신규 파서는 **이 파일에만** 필요.
  - 구조화된 Tasks 전용 뷰(또는 뷰 모드) 렌더링.
  - "태그 이름 -> 대상 파일" 매핑 + 그 파일 원문에서 번호/ID 문자열을 찾는 범용 검색(대상 문서 자체는 깊이 파싱하지 않음) - 설정으로 매핑을 바꿀 수 있게 함(다른 프로젝트의 다른 태그/파일명 지원).
  - 같은 스펙 안에서: 요구사항/버그픽스 조항 번호, 다른 작업 번호, 업무프로세스 제목으로의 문서 전환 + 해당 텍스트 위치로 이동.
- **제외**:
  - 스펙을 넘나드는 참조 이동(해당 태그 자체가 스펙 내부 참조만 쓰므로 범위 밖).
  - `tasks.md` 자체의 편집(체크박스 토글 등) - 조회 전용.
  - 대상이 다이어그램 펜스(예: `biz-process.md`가 나중에 dg `bizprocess`/`bpmn` 펜스를 쓰게 될 경우)일 때 다이어그램 **내부** 특정 노드까지 하이라이트하는 것 - 해당 블록까지 이동하는 것으로 충분(범위 밖, 범용 텍스트 검색의 자연스러운 한계).

**수정(사용자 피드백)**: 이 기능을 `.kiro` 모드에 고정하지 않는다. "방법론"은 절차(어떤 파일이 작업 목록인지), 양식(그 파일이 쓰는 태그/표기 체계), 액션(태그가 어떤 이동을 일으키는지)을 포함하는 구조 설정 그 자체다 - 즉 "방법론 설정"은 단순 태그->파일 매핑표가 아니라, **어떤 디렉터리 구조에서 어떤 파일이 작업 목록 역할을 하는지 자체도 설정이 결정한다.** `.kiro`의 현재 파일명(`tasks.md`/`requirements.md`/`biz-process.md`/`bugfix.md`)과 5개 태그는 spec-viewer가 기본으로 들고 있는 **기본 설정값**일 뿐, 코드에 하드코딩된 전제가 아니다. spec-kit 모드가 지금은 이 구조의 기본 설정을 안 가지고 있어 자연히 아무 것도 안 뜨지만, 그건 "spec-kit은 범위 밖"이어서가 아니라 "spec-kit용 기본 설정이 아직 없어서"다 - 나중에 spec-kit용 설정을 추가하면 그대로 동작해야 한다.

## 경계 후보
세 경계가 각각 하나의 책임만 진다(설계에서 모듈/파일 단위로 구체화):
- **방법론 설정**(데이터): **어떤 파일이 작업 목록인지**(절차) + **그 파일이 쓰는 태그/표기 체계**(양식: 태그->파일 매핑, DONE/`_DoneWhen:_` 같은 이표기) + **태그가 일으키는 이동**(액션)까지 포함하는 구조 설정 전체를 담는 신규 설정 자리(가칭 `spec::methodology_settings` 또는 `.kiro/settings/` 아래 신규 파일) - 읽기 전용 선언, 파싱 로직을 갖지 않는다. `.kiro`용 값(`tasks.md`가 작업 목록, 5개 태그)은 이 설정의 **기본값**이지 코드에 박힌 전제가 아니다.
- **Tasks 파서**: `tasks.md` 원문 -> 구조화 모델(작업 번호, 체크박스, `(P)`, 태그 줄). 기존 `spec::progress::count_progress`(평면 집계)는 그대로 두고 건드리지 않음.
- **방법론 보기 + Navigator**(동작): 구조화 Tasks 뷰 렌더링(가칭 `ui::tasks_panel`, 기존 `ui::doc_panel`과의 분리/통합 여부는 설계 결정)과, 메타 태그 선택 시 "방법론 설정"의 매핑으로 대상 파일을 찾고 원문 텍스트 검색으로 위치를 찾아 이동을 실행하는 Navigator. UI 구조는 기존 **트리(좌, 내비게이션) + 뷰어(우, 내용)** 2패널 그대로 유지한다(토론 중 사용자가 명시적으로 확정) - 새 3번째 패널이나 별도 화면을 만들지 않는다. 같은 문서 내 위치면 뷰어만 스크롤, 다른 문서로 가면 트리의 선택 상태를 그 문서로 옮기고 뷰어가 새 위치를 보여준다 - 둘 다 기존 "트리 선택 -> 뷰어 갱신" 흐름(`load_selected_doc`)의 변형이지 새로운 패널 체계가 아니다.
- 신규 "같은 스펙 안에서 문서 전환 + 특정 위치로 스크롤" 액션(Navigator가 호출) - 기존 `scroll_to`/`jump_heading`(현재 문서 내부 전용)과는 별개의 새 메커니즘이 필요하지만, 위 2패널 틀 안에서 동작한다.

## 경계 밖
- 다른 스펙의 `tasks.md`/`requirements.md`로의 참조(태그 문법 자체가 스펙 내부 참조만 지원).
- `tasks.md` 작성/편집 보조(새 작업 추가, 체크박스 토글 등).
- spec-kit 등 다른 모드용 기본 설정을 **이 스펙 안에서 새로 만드는 것** - `.kiro`용 기본 설정 하나만 이 스펙에서 제공하고, 구조 자체는 설정 가능하게 열어둔다(위 수정 참고). 다른 모드용 설정 추가는 별도 작업.

## 상류 / 하류
- **상류**: `spec::build`가 이미 읽어들인 스펙 디렉터리 스냅샷(`SpecDirSnapshot`/`FileSnapshot`), 기존 `count_progress`의 체크박스 인식 규칙(동일한 `[x]`/`[X]`/`[ ]`/`[ ]*` 패턴을 신규 파서도 따라야 함 - SSoT 중복 방지 검토 필요).
- **하류**: 트리 패널의 진행률 배지 표시 방식에 영향을 줄 수 있음(더 세분화된 정보를 보여줄지는 설계에서 결정). `app::search`(문서 내 검색)와의 상호작용도 설계에서 점검 필요(구조화된 뷰에서 텍스트 검색이 어떻게 동작하는지).

## 기존 스펙 접점
- **확장**: `spec-viewer`(원본 스펙) - `tasks.md` 취급은 원래 이 스펙의 Scope(`spec::progress`, `DocKind::Tasks`)에 속하지만, 이번 요청(구조화된 뷰 + 크로스 참조 이동)은 그 범위를 명백히 넘어서는 신규 능력이라 별도 스펙으로 분리.
- **인접**: `spec-viewer-kiro-folder-groups`(트리의 `Dir`/`File` 노드 체계 - 이번 기능은 `.kiro` 스펙 트리 쪽에만 적용되므로 영향 적음), `spec-viewer-files-mode-sort`(가장 최근에 태그 체계를 실제로 많이 쓴 `tasks.md` 예시 제공).

## 제약
- Rust/ratatui TUI 환경 - 마우스 클릭 또는 키보드만으로 "링크 선택 -> 이동"을 구현해야 함(브라우저의 하이퍼링크 클릭과 다름). UI는 트리+뷰어 2패널 틀을 유지(위 경계 후보 참고).
- "방법론 설정"(태그->파일 매핑, 표기 이표기)을 실제 설정으로 두려면 **신규 설정 인프라**가 필요하다 - `grep -rn "\.kiro/settings\|config_path\|read_config\|Settings\b" src`로 전수 확인한 결과 spec-viewer는 지금 설정 파일 개념이 전혀 없고 전부 `clap` CLI 플래그뿐이다(cited). 기본 매핑(`_Requirements:_`/`_Boundary:_`->requirements.md/bugfix.md, `_BizProcess:_`->biz-process.md, `_Depends:_`->자기 자신)을 하드코딩 기본값으로 두고, 설정 파일로 덮어쓰는 구조가 될지는 설계에서 확정 - "작은 기능 하나"가 아니라 이 스펙의 범위에 신규 설정 체계 도입이 포함된다는 뜻.
- 기존 `markdown::render`/`doc_panel` 파이프라인과의 공존 또는 대체 범위를 설계에서 명확히 해야 함(완전 별도 렌더러 vs 기존 렌더러 확장).
- `biz-process.md` 참조 대상과 관련: dg(0.3.0+, 현재 핀 `c730981`)는 이미 ` ```bizprocess `/` ```biz-process `/` ```bpmn ` 펜스 언어를 인식해 BPMN 드릴다운으로 렌더할 수 있다(cited: `dg::diagram::language_of_fence`, `src/markdown/mermaid/engine/dg_engine.rs::render_other_language`가 이걸 그대로 위임 - spec-viewer 쪽 코드 변경 없이 이미 연결돼 있음). 다만 현재 이 저장소의 실제 `biz-process.md`들은 전부 평문 드릴다운 표기이고 이 펜스를 쓰지 않는다(cited, 직접 확인). 원문 텍스트 검색 방식(위 접근)이라 이 차이에 영향받지 않지만, "biz-process.md를 실제로 bizprocess 펜스로 바꿀지"는 이 스펙과는 별개의 결정이다.
- 이번 세션에 반영된 `methodology` 서브모듈 갱신으로 `tasks.md`의 `DONE` 태그가 신규 스펙부터 `_DoneWhen:_`로 바뀌었다 - 신규 파서는 두 표기를 모두 인식해야 함(기존 완료 스펙들은 `DONE` 표기를 그대로 유지하므로).
- **(사용자 피드백 반영) `value-chain.md`/`biz-process.md` 형식이 `../agentic-psdd`에서 아직 조정 중이다** - 확정 전. 확정되는 대로 **이전 형식(기존 완료 스펙들이 쓰는 들여쓰기+`L2-D1`류 ID 방식)과 새 형식(현재 draft인 제목 깊이 방식, 또는 그 이후 더 바뀔 수 있는 형식)을 병행 지원**해야 한다(위 요구사항 5.5). Navigator가 대상 문서를 구조적으로 파싱하지 않고 태그 값 문자열을 원문에서 찾는 방식(위 접근)이라 이 요구는 설계 변경 없이 이미 충족되지만, 이 사실을 우연이 아니라 **명시적 요구사항**으로 못박아 둔다 - 나중에 누군가 "효율을 위해 형식별 전용 파서를 추가하자"고 제안해도 이 요구사항이 그 제안을 걸러낸다.

## 근거
- **찬성 근거**:
  - cited: `src/spec/progress.rs` 모듈 문서 주석이 "번호, 중첩을 파싱하지 않는다"고 스스로 명시 - 현재 한계가 코드에 이미 자인되어 있음.
  - cited: 코드 전수 검색(`grep -n "jump\|goto\|navigate"`)으로 크로스 문서 이동 기능이 전혀 없음을 확인.
  - cited: 사용자가 토론 중 명시적으로 "전용 Tasks 뷰"를 선택하고 "링크 찾아가기도 되게" 요구 추가.
- **반대 근거**:
  - assumption: 이 세션에서 지금까지 쌓인 스펙 11개 중 실제로 태그(특히 `_BizProcess:_`)를 꾸준히 쓰는 건 최근 2~3개 스펙뿐이라, 투자 대비 실사용 빈도는 아직 검증되지 않음.
